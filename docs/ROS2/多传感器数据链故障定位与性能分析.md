# Day 1：Latency 分层

这是今天最重要的实验。

先不要急着用 perf。

我们自己制造一个传感器数据链。

---

## 1. 创建模拟 Sensor

写一个 C++ node：

```text
sensor_sim
```

发布：

```text
/sim/camera
```

频率：

```text
30 Hz
```

消息：

```cpp
sensor_msgs::msg::Image
```

每一帧：

```text
frame_id = camera_link
timestamp = sensor_time
```

---

# 2. 建立四个时间点

不要只记录：

```cpp
header.stamp
```

这一次记录：

```text
T0 = sensor timestamp
T1 = publish 前
T2 = callback 开始
T3 = callback 结束
```

形成：

```text
T0                         T1
│                          │
│   driver / preparation   │
│─────────────────────────>│
                           │
                           publish
                             │
                             ▼
                           DDS
                             │
                             ▼
                           T2
                           │
                           │ callback
                           │
                           ▼
                           T3
```

于是可以计算：

```text
Driver delay = T1 - T0

Transport + scheduling =
T2 - T1

Callback processing =
T3 - T2
```

这一步非常关键。

---

# 3. 注意一个现实问题

`T1` 和 `T2` 如果来自不同进程：

```text
Publisher process
Subscriber process
```

那么不能简单认为：

```text
steady_clock 时间天然可直接比较
```

尤其真实机器人可能存在：

```text
不同机器
不同 clock
NTP/PTP
system clock
steady clock
sensor hardware clock
```

所以 Week 7 后面会专门讨论：

> **Clock domain 到底是什么？**

目前实验先放在**同一台机器、同一个 clock domain**里。

---

# Day 1 实验目标

最终打印：

```text
frame=100
sensor_age=8.2ms
transport_sched=2.4ms
callback=1.1ms
total=11.7ms
```

然后人为增加：

```cpp
sleep_for(50ms);
```

分别放在：

### A. publish 前

```text
Driver delay ↑
```

### B. subscriber callback 前制造 Executor 阻塞

```text
Executor delay ↑
```

### C. callback 内 sleep

```text
Processing time ↑
```

这三个实验得到的现象应该不同。

# Day 2：Queue / Backlog

今天研究一个机器人里极其常见的问题：

> **消息为什么越积越多？**

建立：

```text
Publisher
    │
    │ 30Hz
    ▼
 DDS Queue
    │
    ▼
Subscriber
    │
    │ callback 只能处理 10Hz
    ▼
Algorithm
```

生产：

```text
30 msg/s
```

消费：

```text
10 msg/s
```

那么 backlog：

```text
30 - 10 = 20 msg/s
```

持续运行以后：

```text
Queue
0
 ↓
20
 ↓
40
 ↓
60
 ↓
...
```

最终：

```text
Memory ↑
Latency ↑
Drop ↑
```

---

# 这就是一个非常重要的因果链

```text
Processing slower
       ↓
Consumer < Producer
       ↓
Queue accumulation
       ↓
Message age ↑
       ↓
Latency ↑
       ↓
Queue full
       ↓
Message drop
```

所以：

> **“消息延迟”有时候根本不是网络慢，而是消费者处理不过来。**

这在 Camera / PointCloud2 上尤其重要。

---

# Day 2 实验

发布：

```text
Camera 30Hz
```

Subscriber：

```cpp
sleep_for(50ms);
```

理论上：

```text
30Hz → 33.3ms/frame
```

但：

```text
callback = 50ms
```

消费能力：

```text
20Hz
```

所以：

```text
Producer = 30Hz
Consumer = 20Hz
```

必然产生积压。

---

# 观察三个东西

同时运行：

```bash
ros2 topic hz /sim/camera
```

以及你的程序打印：

```text
header.stamp
now()
age
```

再观察：

```bash
top
```

以及：

```bash
top -H
```

你应该看到：

```text
CPU
Queue
Latency
```

开始发生关联。

# Day 3：Message Drop

今天研究：

> **消息丢失到底是不是网络丢包？**

先做一个非常简单的实验。

Publisher：

```text
sequence = 0
1
2
3
4
...
```

Subscriber：

```text
last_sequence
```

如果：

```text
收到：

100
101
102
105
106
```

那么：

```text
103、104
```

发生了什么？

---

# 不要直接说“DDS丢包”

因为可能有很多原因：

```text
103 / 104
│
├── Publisher没发
│
├── DDS transport丢失
│
├── QoS导致样本被丢弃
│
├── Queue overflow
│
├── Subscriber处理不过来
│
└── Executor延迟
```

因此你需要进一步实验。

---

# BEST_EFFORT

```text
Publisher
   ↓
DDS
   ↓
Subscriber
```

发生丢失时：

```text
不保证重传
```

适合某些：

```text
Camera
LiDAR
```

场景。

---

# RELIABLE

理论上：

```text
Publisher
   ↓
DDS
   ↓
ACK
   ↓
确保可靠传输
```

但可靠性并不是免费的。

可能带来：

```text
重传
队列
内存
CPU
延迟
```

所以：

> QoS 是系统设计参数，不是简单的“越可靠越好”。

---

# Day 4：Out-of-order

今天研究：

> **消息为什么乱序？**

构造：

```text
Sensor:
100
101
102
103
104
```

人为制造：

```text
102 延迟
```

于是 subscriber：

```text
100
101
103
104
102
```

现在你要观察：

```text
sequence order
timestamp order
callback order
```

三者可能并不完全一样。

---

# 特别注意

```text
callback order
```

不一定等于：

```text
sensor timestamp order
```

例如 MultiThreadedExecutor：

```text
Message A
Message B
```

可能：

```text
A → ready
B → ready

Thread 1 → A
Thread 2 → B
```

最终：

```text
B callback finish
A callback finish
```

因此：

```text
callback completion order
≠
message timestamp order
```

这就是为什么算法层需要认真设计同步策略。

# Day 5：CPU + Executor

现在把你前面 Week 3～5 的知识全部接进来。

模拟：

```text
Camera 30Hz
LiDAR 10Hz
IMU 200Hz
```

三个 callback：

```text
Camera callback = 10ms
LiDAR callback  = 20ms
IMU callback    = 1ms
```

---

## SingleThreadedExecutor

理论模型：

```text
Camera
   ↓ 10ms

LiDAR
   ↓ 20ms

IMU
   ↓ 1ms
```

如果 Camera / LiDAR 连续执行：

```text
IMU
```

可能出现：

```text
callback delay ↑
jitter ↑
```

---

## MultiThreadedExecutor

可能变成：

```text
Thread 1
Camera ──────10ms

Thread 2
LiDAR ─────────────20ms

Thread 3
IMU
 │ │ │ │ │
```

IMU 受到的影响可能降低。

但注意：

> **MultiThreadedExecutor 不一定更快。**

因为还可能引入：

```text
lock contention
cache contention
context switch
CPU competition
```

这正好与你之前的实验连接起来。

---

# Day 5 必做实验

比较：

```text
SingleThreadedExecutor
vs
MultiThreadedExecutor
```

记录：

```text
IMU latency
IMU jitter
Camera latency
LiDAR latency
CPU
context switch
```

最终不要只得出：

> MultiThreadedExecutor 更快。

而应该得到类似：

```text
SingleThreaded:
IMU p99 = 35ms

MultiThreaded:
IMU p99 = 4ms

但 CPU:
Single = 42%
Multi = 58%
```

于是你的工程判断就是：

> **用 CPU 换实时性。**

这才是性能优化。

# Day 7：综合故障定位

最后一天给自己制造一个真实事故。

---

## 故障现象

假设：

```text
Camera
30Hz

LiDAR
10Hz

IMU
200Hz
```

系统运行一段时间以后：

```text
Camera latency
20ms → 40ms → 80ms → 150ms

IMU
出现明显 jitter

CPU
80%
```

现在不要直接改代码。

按照：

```text
现象
 ↓
假设
 ↓
实验
 ↓
证据
 ↓
结论
```

开始定位。

---

# 第一问：Sensor 正常吗？

检查：

```text
timestamp
frequency
sequence
```

如果：

```text
Camera timestamp
本身已经落后
```

那么：

```text
ROS2/DDS
```

可能根本没问题。

---

# 第二问：Publisher 正常吗？

测：

```text
T_sensor
T_publish
```

如果：

```text
T_publish - T_sensor
```

已经：

```text
100ms
```

那么问题在：

```text
Driver / preprocessing
```

---

# 第三问：DDS 正常吗？

如果：

```text
publish
 ↓
DDS
 ↓
receive
```

这一段明显增加：

```text
latency
```

才考虑：

```text
QoS
DDS queue
network
serialization
transport
```

---

# 第四问：Executor 正常吗？

如果：

```text
DDS receive
```

已经到了 subscriber，

但是：

```text
callback start
```

很晚：

```text
receive = T1
callback = T2

T2 - T1 = 80ms
```

那么重点查：

```text
Executor
Scheduler
CPU
callback blocking
```

---

# 第五问：Callback 正常吗？

如果：

```text
callback start
callback end
```

之间：

```text
100ms
```

那么：

```text
Algorithm
```

才是主要嫌疑。

---

# 最终形成一张 RCA 表

| 阶段                           |       时间 | 判断     |
| ---------------------------- | -------: | ------ |
| Sensor → Message             |      5ms | 正常     |
| Message → Publish            |      3ms | 正常     |
| Publish → DDS Receive        |      8ms | 正常     |
| DDS Receive → Callback Start | **80ms** | **异常** |
| Callback Start → End         |      5ms | 正常     |

最终结论：

> **不是 Camera，也不是 DDS transport，而是 Executor/调度侧存在 80ms 的执行等待。**

然后再继续：

```text
Executor
 ↓
线程状态
 ↓
CPU
 ↓
Scheduler
 ↓
其他 callback
 ↓
锁
```

这才叫**问题定位**。

---

# Week 7 最终能力

到这里，你就应该能够把：

```text
“ROS2 Camera 延迟”
```

从一个模糊问题：

```text
ROS2很慢
```

变成一个可以测量的模型：

```text
Latency_total

= T_publish - T_sensor
+ T_DDS
+ T_executor
+ T_callback
```

然后继续向下拆：

```text
T_DDS
├── serialization
├── queue
├── transport
├── deserialization
└── rmw

T_executor
├── callback ready
├── executor wait
├── scheduler
├── CPU contention
└── lock

T_callback
├── algorithm
├── memory
├── cache
└── blocking
```

**这一步非常重要。**

因为从你之前做 Fast DDS 的经历来看，你真正应该强化的并不是“会不会 ROS2”，而是：

> **当 ROS2 出现性能问题时，你能不能沿着 `rclcpp → rcl → rmw → Fast DDS → Linux` 建立证据链，而不是凭经验猜是哪一层。**

Week 7 就围绕这个能力展开。
