# 1. 第一层：谁产生数据？

先不要管算法。

只问：

> **这个 Topic 的数据到底是谁生产的？**

例如：

| 数据                | Producer          |        典型频率 | 数据特点 |
| ----------------- | ----------------- | ----------: | ---- |
| Camera Image      | Camera Driver     |    15~30 Hz | 大    |
| Camera CameraInfo | Camera Driver     |    15~30 Hz | 小    |
| LiDAR PointCloud  | LiDAR Driver      |    10~20 Hz | 很大   |
| IMU               | IMU Driver        | 100~1000 Hz | 小    |
| TF                | TF Broadcaster    |   10~100 Hz | 小    |
| Object Detection  | Perception        |     5~20 Hz | 中    |
| SLAM Pose         | SLAM              |    10~30 Hz | 小    |
| Map               | SLAM / Map Server |          低频 | 很大   |
| Path              | Nav2              |     1~20 Hz | 中    |
| cmd_vel           | Controller / Nav2 |    10~50 Hz | 很小   |

这里你已经可以开始建立一个非常重要的意识：

> **机器人系统中，不是所有 Topic 都一样。**

例如：

```text
IMU:
100~1000 Hz
几十~几百 Bytes

Image:
30 Hz
几百 KB ~ 数 MB

PointCloud:
10 Hz
几百 KB ~ 数 MB

cmd_vel:
50 Hz
几十 Bytes
```

所以：

**不能只看 Topic 数量。**

真正影响系统压力的是：

```text
数据频率 × 单条消息大小 × 消费者数量
```

# 2. Camera：数据大户

假设 RGB Camera：

```text
1920 × 1080
30 FPS
RGB8
```

一帧原始数据：

```text
1920 × 1080 × 3
≈ 6.22 MB
```

30 FPS：

```text
6.22 MB × 30
≈ 186 MB/s
```

注意：

> 这还只是原始数据量，不等于实际网络/DDS流量。

如果使用：

```text
JPEG
H264
H265
```

数据量会明显下降。

所以你以后看到：

```text
/image_raw
```

第一反应应该是：

> **这是一个高带宽 Topic。**

然后马上查：

```text
频率？
消息大小？
发布进程？
订阅进程？
QoS？
是否跨进程？
是否跨机器？
是否发生拷贝？
```

# 3. LiDAR：另一种数据大户

例如 LiDAR：

```text
10 Hz
100,000 points/frame
```

假设一个 Point：

```text
x
y
z
intensity
```

如果每个字段 4 Bytes：

```text
16 Bytes / point
```

那么：

```text
100000 × 16
= 1.6 MB/frame
```

10 Hz：

```text
≈ 16 MB/s
```

这时候你会发现：

```text
Camera
    ↓
几十~几百 MB/s

LiDAR
    ↓
几~几十 MB/s

IMU
    ↓
几 KB/s
```

所以系统优化的时候：

**不能把所有 Topic 当成同一个等级。**

---

# 4. IMU：数据小，但频率高

IMU 很典型：

```text
100 Hz
200 Hz
500 Hz
1000 Hz
```

每条消息可能只有几十到几百 Bytes。

例如：

```text
IMU
  ↓
1000 Hz
  ↓
小消息
```

它的特点不是：

> 带宽特别大

而是：

> **调度频率非常高。**

这就开始进入你的核心领域：

```text
IMU
 ↓
DDS receive
 ↓
Executor
 ↓
callback
 ↓
TF
 ↓
SLAM
```

如果 callback：

```text
1 ms
```

那么 1000 Hz：

```text
1000 × 1 ms
```

系统已经有很明显的 CPU 调度压力。

所以：

> **高频小消息主要关注 CPU、调度、callback latency。**

而：

> **低频大消息主要关注带宽、内存、拷贝、序列化。**

这个区别非常重要。

# 5. TF2：不是“数据源”，而是坐标关系系统

这里特别容易理解错。

比如：

```text
base_link
   │
   ├── camera_link
   │
   ├── lidar_link
   │
   └── imu_link
```

TF2 本质上维护：

```text
Frame A
   ↓
Frame B
```

之间的：

```text
translation
rotation
timestamp
```

例如：

```text
base_link → camera_link
```

表示：

> Camera 相对于机器人本体在哪里。

---

## TF2 为什么这么重要？

因为：

```text
Camera
LiDAR
IMU
```

通常都有自己的坐标系。

例如：

```text
camera_link
lidar_link
imu_link
base_link
odom
map
```

感知算法不能简单地：

```text
拿数据直接算
```

而需要：

```text
Sensor Data
     ↓
timestamp
     ↓
TF lookup
     ↓
Transform
     ↓
统一坐标系
```

所以你前面学的：

```text
timestamp
TF
DDS
Executor
```

现在终于连起来了。

# 7. SLAM：不要研究算法，先研究输入输出

你完全不需要现在去研究：

```text
ICP
GICP
LOAM
ORB-SLAM
Graph Optimization
Loop Closure
Bundle Adjustment
```

对你来说，先把 SLAM 看成一个黑盒：

```text
┌─────────────────────┐
│        SLAM         │
│                     │
│   输入 → 算法 → 输出 │
└─────────────────────┘
```

输入可能：

```text
LiDAR
IMU
Camera
Odometry
TF
```

输出：

```text
Pose
Map
TF
Odometry
```

例如：

```text
LiDAR ───────┐
             │
IMU ─────────┼──► SLAM ───► Pose
             │
TF ──────────┘             │
                            ▼
                           Nav2
```

你的问题永远是：

> SLAM 收了什么？

> 多快？

> 消费 CPU 多少？

> 输出什么？

> 输出频率多少？

> 延迟多少？

而不是：

> SLAM 算法内部用了什么优化器？

# 12. Week 9 最重要的一个公式

以后看到任何 ROS2 Topic，先估算：

```text
Bandwidth ≈ Message Size × Frequency × Number of Consumers
```

例如：

```text
Image:
6 MB × 30 Hz × 2 consumers
≈ 360 MB/s
```

这时候你马上应该想到：

```text
内存拷贝
序列化
DDS
网络
CPU
缓存
```

而：

```text
IMU:
200 B × 1000 Hz × 2
≈ 400 KB/s
```

带宽完全不是一个量级。

但它会带来：

```text
1000 callback/s
```

所以：

```text
大消息 → 带宽 / 内存 / copy / serialization

高频消息 → CPU / scheduling / callback / latency

高实时控制 → jitter / scheduling / priority / deadline
```

这三类问题要分开看。

# 13. 今天的实验：不要写算法，做“系统体检”

你现在可以直接拿你们机器人的 ROS2 系统做。

### Step 1：列所有 Node

```bash
ros2 node list
```

---

### Step 2：找 Topic

```bash
ros2 topic list
```

---

### Step 3：观察频率

例如：

```bash
ros2 topic hz /imu/data
ros2 topic hz /camera/image_raw
ros2 topic hz /scan
```

---

### Step 4：观察消息类型

```bash
ros2 topic type /imu/data
ros2 topic type /camera/image_raw
```

---

### Step 5：观察 Publisher / Subscriber

```bash
ros2 topic info /imu/data -v
```

重点看：

```text
Publisher count
Subscription count

Node name
Node namespace

QoS profile
```

---

### Step 6：观察消息大小

```bash
ros2 topic bw /imu/data
```

以及：

```bash
ros2 topic bw /camera/image_raw
```

这个非常值得你做。

你会第一次直观看到：

```text
哪个 Topic 真正在“吃带宽”
```
