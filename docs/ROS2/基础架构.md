## talker -> listener 源码链

1. 发布端调用栈到 Fast DDS 的 DataWriter::write()（序列化 + UDP 发送）就结束了，是一次同步单向调用，函数随即返回。
2. topic_callback 发生在订阅者进程（另一个进程/另一个线程）中，由订阅者的 Executor 事件循环驱动。
3. 订阅侧的路径也不是严格的 Fast DDS → rmw → rcl → rclcpp 线性回传：Fast DDS 接收线程只是把数据放进 DataReader 队列并触发 on_data_available / StatusCondition；真正取消息是 executor 循环里的 rcl_take → rmw_take，即"等待-唤醒-主动拉取"（wait/take）模型，而非"推送到 callback"。

另外补充一点：如果 pub 和 sub 在同一个进程且开启了 intra-process 通信，消息会完全绕过 rcl/rmw/Fast DDS，直接走 IntraProcessManager。

```text
[发布进程]                                      [订阅进程]
timer_callback
 └─ Publisher::publish
     └─ do_inter_process_publish
         └─ rcl_publish (rcl/publisher.c)
             └─ rmw_publish (rmw_fastrtps_cpp)
                 └─ __rmw_publish (rmw_fastrtps_shared_cpp)
                     └─ DataWriter::write ──UDP──►  DataReader 队列
                                                       └─ SubListener::on_data_available (步骤7)
Executor::spin_some_impl                              ▲ 触发 StatusCondition
 └─ wait_for_work ── rcl_wait ── rmw_wait ── WaitSet::wait ◄┘   (被唤醒)
     └─ get_next_ready_executable
         └─ execute_any_executable
             └─ execute_subscription
                 ├─ take:  take_type_erased → rcl_take → rmw_take_with_info
                 │          → __rmw_take → DataReader::take (反序列化)
                 └─ handle: handle_message → AnySubscriptionCallback::dispatch
                              └─ topic_callback  ✅
```

## 为什么 ROS2 不直接调用 Fast DDS，而要分这么多层

### 1. rmw 层：让中间件可以整体替换

这是分层的**最核心动机**。`rmw/include/rmw/rmw.h` 只是一份纯 API 声明（约 150 个函数签名），不含任何实现。任何 DDS 厂商只要实现这份接口，就能接入 ROS 2：

- Fast DDS（你工作区里的 `rmw_fastrtps_cpp`）
- Cyclone DDS、RTI Connext、GurumDDS……

你甚至不需要重新编译应用代码，只需设置环境变量即可切换：

```bash
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
```

一个旁证：同一个 Fast DDS 在你的工作区里就有**两个**实现——`rmw_fastrtps_cpp`（静态类型支持，编译期生成）和 `rmw_fastrtps_dynamic_cpp`（运行时动态解析类型，无需代码生成）。没有 rmw 抽象层，这种"一 DDS 两实现"根本无法并存。

### 2. rcl 层（C 语言）：让所有客户端语言共享同一套核心

rcl 是纯 C 写的。这一层的价值是：**节点语义只实现一次，所有语言复用**。

围绕"节点"的核心逻辑——命令行参数解析、topic 重映射（remap）、命名空间展开、ROS graph 查询、时间系统、日志——全部在 `rcl/src/rcl/` 里。然后：

- `rclcpp`（C++）
- `rclpy`（Python）
- `rclc`（嵌入式极简客户端）
- `rcljava`、`rclnodejs`……

都只是对 rcl 的薄封装加上各自语言的惯用法。如果 C++ 直接调 Fast DDS，Python 就得把这套逻辑用 Python 再写一遍，两边还很容易行为不一致。

### 3. ROS 概念和 DDS 概念根本不是一回事

DDS 原生世界里**没有**"ROS topic/service/action"，只有 DataWriter/DataReader。中间这些层做的正是"翻译"工作，你之前追过的代码里随处可见：

- **名字改写（mangling）**：ROS 的 `/topic` 在 DDS 里要变成 `/rt/topic`，service 变成 `/rq/...`、`/rr/...`，见 [namespace_prefix.cpp](file:///home/user/workspace/ros2_debug_ws/src/rmw_fastrtps/rmw_fastrtps_shared_cpp/src/namespace_prefix.cpp)。DDS 规范不允许以 `/` 开头的 topic 名，不翻译就直接报错。
- **QoS 映射**：ROS 的 QoS 语义（如 `BEST_EFFORT` + `KEEP_LAST`）到 DDS QoS 的转换及兼容性检查，见 [qos.cpp](file:///home/user/workspace/ros2_debug_ws/src/rmw_fastrtps/rmw_fastrtps_shared_cpp/src/qos.cpp)。
- **service/action 是 ROS 层概念**：DDS 根本没有 service。rcl 用"一对 request/reply topic"把 service 拼出来；action 又用三个 topic + 状态机拼出来（`rcl_action/`）。这些都必须放在 DDS 之上。
- **类型系统解耦**：rosidl 生成的 C type support 独立于 DDS。`rmw_fastrtps_cpp` 里的 `TypeSupport.hpp` 就是那座桥，负责把 ROS 消息序列化进 DDS 的 wire format。

### 4. 独立演进、独立测试

每层有独立的版本、测试和 [QUALITY_DECLARATION](file:///home/user/workspace/ros2_debug_ws/src/rcl/rcl/QUALITY_DECLARATION.md)（质量等级声明，这关系到能否用于自动驾驶等安全关键场景）。rmw API 保持稳定后，Fast DDS 升级不会波及上层；反之亦然。

可以这么说，但要说得更准确一点：**rcl 是"ROS 客户端语义核心"，而不是整个系统的核心**。ROS 2 实际上有两个核心，各管一摊。

### 5. rcl 是 ROS 特性的核心

```
        ┌─────────────────────────────────────┐
        │  rclcpp / rclpy / rclc  （语言壳）    │
        ├─────────────────────────────────────┤
        │  rcl —— ROS 语义核心（"ROS 的大脑"）   │  ← 你说的这层
        ├─────────────────────────────────────┤
        │  rmw —— 中间件抽象接口                │
        ├─────────────────────────────────────┤
        │  rmw_fastrtps / rmw_cyclonedds ...   │
        ├─────────────────────────────────────┤
        │  Fast DDS / Cyclone —— 通信核心（引擎）│
        └─────────────────────────────────────┘
```

看 rcl 源码目录（你工作区里的 `src/rcl/rcl/src/rcl/`）装的就是一切"很 ROS"的东西：

| 文件 | 职责 |
|---|---|
| `node.c` | 节点的定义、命名空间 |
| `remap.c` / `arguments.c` | 命令行重映射、参数解析（`--ros-args -r ...`） |
| `expand_topic_name.c` | `~/topic`、相对名展开 |
| `graph.c` | `ros2 node list` / `ros2 topic list` 背后的图查询 |
| `wait.c` / `timer.c` | 等待集、定时器原语 |
| `time.c` / `clock` | ROS 时间（含 `/clock` 模拟时间） |
| `logging.c` | 日志后端框架 |
| `security.c` / `localhost.c` | SROS2 安全、仅本机通信策略 |


### 6. 但要注意：不是所有"核心"都在 rcl 里

避免把结论推得太远，有几样重要的东西不在 rcl：

- **参数系统（parameters）**：主要在 rclcpp/rclpy 实现（参数服务、回调、`ros2 param` 的交互端），rcl 只提供少量支撑。
- **Executor / 回调调度模型**：是 rclcpp 的概念，rcl 只给 `rcl_wait` 原语。
- **Action**：在 `rcl_action`（与 rcl 平级的独立包）。
- **生命周期节点**：在 `rcl_lifecycle`。
- **消息类型定义与代码生成**：rosidl 工具链，和 rcl 平级。
